# Prompt 6 — Fix Numeric Safety, Threshold Overflow, CRC, and Independent Test Vectors

Continue on `hardening/opt4001-industry-readiness`. Complete only this prompt, commit, sync, and stop.

## Findings from exploration report

Numeric and vector gaps:

- `rawToLux(uint8_t exponent, uint32_t mantissa)` shifts without validating exponent/mantissa bounds.
- Caller exponent >= 32 can cause undefined behavior.
- Threshold conversion accepts 4-bit threshold exponents and returns `uint32_t`; register-valid encodings can wrap.
- Tests use implementation-derived expectations in places; industry-grade confidence needs independent vectors.
- Need independent coverage for package LSBs, result decode, CRC, threshold conversion, range/config, conversion-time enum, and address/package validity.

## Goal

Make numeric helpers deterministic and safe, and add independent tests that prove lux/threshold/CRC/config math without relying on the implementation under test.

## Implementation requirements

### `rawToLux` and related helpers

- Validate exponent range before shifting.
- Validate mantissa width before shifting.
- Use `uint64_t` intermediate ADC codes.
- Return `INVALID_PARAM`, saturation, or a clearly documented deterministic result for invalid inputs.
- Do not allow undefined shift behavior.
- Keep API compatibility where practical. If changing return type is required, document migration clearly.

### Threshold conversion

- Avoid overflow for 4-bit threshold exponent values.
- Use `uint64_t` for intermediate threshold ADC codes.
- Define behavior for lux values outside representable threshold range:
  - reject with `INVALID_PARAM`, or
  - saturate with explicit status/flag.
- Do not silently wrap.
- Document threshold register units and rounding/truncation.

### CRC

- Ensure CRC decode validates the correct fields.
- Ensure sample CRC status is preserved.
- Ensure CRC tests are independent and not generated by the production helper.
